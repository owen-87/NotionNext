# funshow.top：18 个未编入索引网址分析与优化方案

检查日期：2026-10-09（北京时间）。本次读取已登录 Search Console、检查线上站点地图及 33 个公开 URL、抽查 Google 网址检查与实时渲染，并审阅本地代码。没有修改网站代码、部署或提交索引验证。

## 结论

当前最优先工作是修复公开页面初始 HTML 的正文与内链输出不稳定，再完善文章内容和发现路径。不能把这 18 个 URL 一概归因于内容质量低，也没有证据证明网站受到处罚或服务器过载。

报告按 sitemap.xml 筛选，总计 33 个 URL：已索引 15（45.5%），未索引 18（54.5%）。未索引包含 11 篇文章和 7 个辅助页面。目标应优先覆盖 11 篇文章及有价值的专题入口，而非机械追求全部网址收录。

## 线上技术证据

### 基础访问和索引标签基本正常

两轮公开 HTTP 抽查覆盖 sitemap 中全部 33 个 URL：均返回 200；包含 index/follow 和指向自身规范版本的 canonical；未发现 X-Robots-Tag 屏蔽。robots.txt 允许站点公开页面，仅禁止 /api/。裸域访问最终到达 www 主域。

这些是本次访问视角的结果，不替代 Googlebot 历史访问日志；不足以排除偶发 5xx、地区性访问故障或资源加载失败。

### 优先问题：初始 HTML 缺少正文，且缓存前后存在差异

首轮响应多数标记 `x-vercel-cache: STALE`，所有 33 页均未提取到 H1，大多数只有标题文字或少量模板文本。随后复查，一些文章恢复正文，但首页、归档、分类和部分文章仍缺少主要内容。

字符数排除了 script/style，但包含 title 和导航，不能当作文章字数，更不是 Google 的收录门槛。第二轮结构化观测保存在同目录 `SEO_INDEX_AUDIT_2026-10-09.json`；第一轮数值来自本次请求输出。站内入链统计只覆盖本次 33 页原始 HTML，不代表完整浏览器渲染后或 Google 已知的链接图。

可确认的是正文输出不一致；“动态主题加载与 ISR/CDN 缓存共同导致”是待验证的工程假设。Google 能执行 JavaScript，所以空壳不意味着必然无法收录，但会增加对后续渲染的依赖，也削弱原始 HTML 中的链接发现。

本地高优先级排查位置：`themes/theme.js` 的 `getBaseLayoutByTheme`（约 192 行）、`useLayoutByTheme`（约 222 行）。它们运行时创建 dynamic 组件；虽已配置 ssr:true，仍需验证冷启动时能否等待主题实际加载。`EmptyPageLayout` 返回 null，需要防止失败被当成成功页面缓存。`pages/_app.js` 现已把 SEO 放在布局之外，能够解释“元信息正常、正文缺失”的现象，但还不能单凭源码确定生产根因。

历史 SEO 计划标记过 SSR 修复完成；本次线上结果说明必须重新进行生产验收，不能把过去的本地测试结果当作当前线上已解决。

## 两类原因的判断

**已发现－尚未索引：先解决发现路径与稳定抓取。** Google 的状态含义是已知 URL 尚未抓取，不直接等于该文章质量差。本站首页/目录初始内容缺失是已经观察到的风险；应补齐真实链接和正文输出，再结合抓取统计及服务器日志判断请求频率、错误和耗时。目前没有数据证明“服务器过载”或“抓取预算不足”。

**已抓取－尚未索引：同时检查渲染完整性与独特价值。** `1-1-10` 的抓取许可与规范网址正常，不能靠再次打开 index 标签解决。两篇读书文章主要呈现概念归纳，建议补充有来源的引用和原创应用；漫画教程有实际步骤，但应完善可复现材料；投资分析应补足来源与 AI 模拟标注。这些是内容审阅后的改进建议，不是 Google 已披露的拒收理由。

另发现 `1-1-6` 标题写 Hermes/Ollama/微信，简介及正文却在介绍 Coze 接微信公众号；与 `1-1-9` 标题主题相近。应先恢复标题与正文一致，再判断是否存在重复，不能直接合并或删除。这是范围外关联质量问题，不计入本次 18 个网址。

## 优化顺序与验收

| 顺序 | 工作 | 验收标准 |
| --- | --- | --- |
| P0：先修技术输出 | 让公开主题布局在服务端稳定加载；确保首页、分类、归档、文章原始 HTML 含主体；查清缓存中的空壳版本 | 冷启动、热缓存、刷新后都能读到标题、正文/列表及真实 href；不能以多刷几次偶尔正常作为通过 |
| P0：部署验证 | 确认修复版本上线，按实际缓存机制刷新受影响页面 | 33 个 sitemap URL 复核无空壳；200、canonical、索引标签一致；关键样本 Google 实时截图含完整主要内容 |
| P1：文章发现路径 | 从已收录且相关的文章链接到这 11 篇文章；分类入口组织成主题学习路径 | 重要文章可从首页/专题页少量点击到达；链接在 HTML 内真实存在，不依赖搜索框 |
| P1：内容改进 | 漫画实测、读书实践案例、投资数据来源；修复标题/正文错配 | 每篇回答明确问题，有独有材料；不能只扩充字数或重写摘要 |
| P2：站点地图策略 | 保留规范、可索引且希望出现在搜索结果中的页面；真实更新 lastmod | 与页面实际修改时间一致；不把所有 lastmod 改为当天；不靠调高 priority 提升收录 |
| P2：提交与复查 | 技术和内容修复后，先对少量重点文章请求索引；相关实例修复后再重启验证 | 记录请求日期、抓取日期与单页索引结果；避免未修改就反复提交 |

`/links` 和隐私政策无需为了让“18”变为零而强行追求收录。分类页若有独立导读和有用文章列表，可以保留索引；若决定对薄页 noindex，应同时从 sitemap 移除且保持可抓取，避免用 robots 屏蔽导致 Google 看不到 noindex。

建议在修复完成后的第 7、14、28 天人工复查：优先看 11 篇文章有无新抓取、是否已索引，再看汇总趋势。此为复查安排，不是保证收录期限，也未创建自动监控。

## 官方依据与范围限制

- [Google：网页索引报告与状态含义](https://support.google.com/webmasters/answer/7440203?hl=zh-Hans)：未收录有多种合理原因，重要规范页才是目标。
- [Google：JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)：抓取、渲染、索引分阶段；服务端输出有助于用户与爬虫。
- [Google：站点地图](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)：提交仅是提示；忽略 priority/changefreq；lastmod 应反映真实重要更新。
- [Google：请求重新抓取](https://developers.google.com/search/docs/crawling-indexing/ask-google-to-recrawl)：请求不保证立即或最终收录，重复请求不会加快处理。
- [Google：有帮助、可靠的内容](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)：重点是原创价值、可靠来源与面向读者的内容。
